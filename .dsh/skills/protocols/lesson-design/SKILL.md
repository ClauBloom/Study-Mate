# 课件设计规范

课件的**唯一约束来源**。讲解角色动手前先读本文件；总控验收课件时按本文件核对。分两类：**必须做到的**（硬要素，缺一不可）与**倾向**（弱约束，按现场判断）。

# 一、硬要素（缺一不可）

1. **真实场景开场**（自顶向下）
   从学生熟悉的真实场景或真实问题切入，**不先抛定义、不先讲底层细节**。开场要让读者产生"哦，原来是这个问题"的落点感。

2. **术语先来历、后定义**
   任何术语**第一次出现前**，先讲清三件事——① 它要解决什么问题 ② 为什么需要它 ③ 它的历史来历（谁在什么背景下提出、之前怎么做、为什么不够用）——**然后**才给定义。术语中英对照（例：直方图均衡化 / histogram equalization）。

3. **权威教材的深度，不做速成课**
   像权威教材一样把知识体系讲透：讲清前提、推导、边界与反例。**内容长没关系**，简洁不等于浅；宁可一课只推进一点，也不要把体系压成提纲。

4. **引导式实作**（见第三节）
   每个知识点配一次动手实作，用"我带你一步步做"的方式，**不把成品甩给学生**；载体由总控与学生确定（见第三节开头），你按载体对应的形态约定做，内核都是第三节那五条。

5. **来源诚实**
   易变/版本相关的内容必须核对官方文档后再写，标注"依据 X 文档"；稳定基础知识标注"通用基础知识（可自行查证）"。**不为凑引用而引用。**

6. **收尾三件事**：阅读任务（对应教材章节 + 一处权威来源）、**与最终目标的关系**（这段知识在学生的整体目标里处于什么位置）、提问提示（"不懂就把这一段复制回会话，加【提问】标记"）。

# 二、一课应包含的内容（弱约束：要素齐全，顺序自由）

一课是完整的自包含学习单元。以下要素**应当包含**，但**顺序与组织方式由你按现场判断**——不要被步骤号捆住手脚（"场景在前、定义在后"已由硬要素 1、2 兜底）：

- **开场**：真实场景 / 故事（硬要素 1）
- **来历**：术语要解决什么问题、为什么出现（硬要素 2）
- **原理**：只讲本课所需的数学与机制，配教材式推导与图示
- **实作**：动手做 + 立刻验证（第三节）
- **检索练习**：即时反馈测验（点选即判）——从记忆中提取比重读更能加深记忆，别只让学生"再看一遍"
- **阅读任务**：教材对应章节 + 一处外部权威来源（尽量推荐一份最优质的一手资料）
- **回扣目标**：与最终目标（`MISSION.md`）的关系 + 一个促人思考的收尾问题

**组织倾向**：
- **分块递进**：篇幅可以长（硬要素 3），但按小块组织，每块给一个可构建的小胜利，别让读者一次扛太多（工作记忆很小）
- **难度落点**：每课落在学生的**最近发展区**——既不是纯复习（无聊），也不是一步跨太远（崩溃）；用 `learning-records/` 校准难度
- **间隔与交错**（技能练习时）：同主题的检索练习分散到几次会话（间隔），练习里适当混合相关主题（交错），比一次灌完记得牢

# 三、实作规范（引导式）

**载体选哪个由总控与学生确定**（开课盘问时，连同配套项目、学习目标一起问清：科目性质、学生熟悉的技术栈、环境、偏好），确定后记进 `<subject_path>/lab/README.md`。你收到载体后按本节约定实现——本节只负责"载体定下来之后，实作长什么样"。

## 通用原则（五条，缺一不可）

这五条才是"Kaggle 风格"的内核，与用什么载体无关：

1. **分步引导**：一小步讲解 + 立刻动手，**不一次抛完整任务**
2. **亲手做**：任务部分**留白**给学生写；成品只放 `lab/solutions/`，供做完后对照
3. **可验证**：每个任务都回答"我怎么知道自己写对了"——断言、测试、期望输出对照、清单勾选
4. **即时反馈**：学生做完立刻能验证，不必等 agent 批改
5. **卡壳先引导**：先带他读错误信息 → 给提示 → 再给线索，**不直接给答案**

## 常见载体的形态约定（载体已定时，照此组织）

| 载体 | `lab/` 下的形态 | 怎么验证 |
|---|---|---|
| Jupyter notebook | `NN-主题.ipynb` | 教程格预执行带输出；任务格后跟 `assert` 自检 |
| 源码 + 测试（JS/TS/Go/Rust/C++…） | `NN-主题/` 目录：源码 + 测试文件 | 跑测试（jest / vitest / go test / cargo test / ctest…） |
| 页面（前端 / 可视化） | HTML + JS 页面 | 眼见效果 + `console.assert` / 截图对照 |
| SQL / 数据查询 | `.sql` 文件 + 期望结果 | 结果集对照 |
| 命令行 / 运维 | 脚本 + 沙箱目录 | 期望输出 `diff` |
| 练习页（数学 / 理论） | 练习页（Markdown/HTML）+ 数值验算脚本 | 关键步骤对照 + 数值验证 |
| 清单（非技术 / 技能） | 检查清单 + 自评记录 | 清单勾选 / 录音复述 / 演示 |

**结构约定**：`lab/NN-主题/`（或 `NN-主题.ipynb`）与课件编号对齐；参考答案统一放 `lab/solutions/`；环境与依赖说明写 `lab/README.md`。

## 每种载体都要做到

- **教程部分带结果**：Python 靠预执行输出；其他语言靠"先跑一遍给他看输出"或贴运行结果
- **任务部分留白**：标 **▸ 你的任务**（要做什么、怎么算过），代码/答案留空
- **自检可跑**：能自动验的写断言或测试；不能自动验的（如前端效果、口语）给明确的自查清单
- **答案折叠**：做完再展开对照，别让它提前剧透

# 四、讲法倾向（弱约束，可被覆盖）

这不是检查表，是一组倾向。目标是学生真的听懂，走哪条路按现场判断。

**问题感** — 先让学生感到"这是个什么麻烦"。他知道麻烦长什么样，概念才有落点。

**具体先行** — 例子走在定义前面。能跑的一小段代码、一个生活场景，都可以当入口。

**小步** — 一次给一点。学生消化的速度比讲完的速度重要。

**学生的语言** — 沿用学生自己的说法。他用得上那个词，才算学会。

**参与** — 留出预测、改一行、复述的空间。学生自己动手或开口时，你能看见他卡在哪一层。

**连回项目** — 把知识与他在做的事接上。有去处的东西不容易忘。

**学生反馈的处理倾向**：
- "没听懂" → 换一个更近的例子，或降一层抽象
- "太简单" → 加边界、加取舍、加反例
- 要答案 → 先给线索；还卡再加码
- "有什么用" → 先答用途，再回内容

**覆盖关系**：这些倾向是默认值。学生的明确要求、科目性质、任务紧急度都可以覆盖它们；`MEMORY.md` 里记录的个人偏好优先级最高——那份文件就是这套指引随人调整的地方。

# 五、记忆与难度（弱约束）

课件与练习的设计要分清两种"会了"：

- **流畅度**：当场能复述、能照做——会给人"学会了"的错觉
- **存储强度**：过一段时间还能想起来、还能用——这才是长期目标

设计时用**合意困难**（有难度、但够得着）：检索练习（回忆而非重读）、间隔（分散到多次会话）、交错（技能练习混合相关主题）。难度落点始终在最近发展区（见第二节）。

# 六、贯穿线索（课程级，与课件呼应）

每课都要连回三条线索，别让学生学完忘了为什么学：

- **最终目标线索**：每课回答"这段知识与学生的最终目标（`MISSION.md`）什么关系"
- **项目线索**：选定的配套项目从早期就作为实作的固定素材，逐课埋线——项目不等到最后才写（项目由总控与学生确定，见总控的盘问）
- **工具线索**（编程类科目）：亲手实现的算法与现成库（OpenCV/scikit-image 等）的结果对照，知道"标准答案长什么样、为什么长这样"

# 七、复用与骨架（硬约束）

- **先读组件库**：读 `<subject_path>/assets/`（至少 `style.css`、`quiz.js`），已课件必须链接已有组件
- **从骨架拷起**：`<root>/templates/lesson.html`（顶栏、主题开关、提问提示、样式脚本引用都已就位，路径就是课件该用的相对路径），再改标题、编号、节点与正文；**别删主题开关**
- **编号递增**：`NNNN-dash-case.html`，取现有最大编号 +1
- **新组件先写进 `assets/`** 再引用，不内联可复用代码；拿不准是否可复用时，先写进 `assets/` 更稳
- 课件是自包含 HTML（相对路径引用共享层 `../../../assets/`、科目组件 `../assets/`、`reference/`），浏览器直接打开即可用
- **美观可回看**：排版干净、层次清晰、适合反复打开查阅——学生会回来复习它，不是看完就扔
