# 课件设计规范

**本文件管课件内核，不管版式**：怎么分节、标题写什么、例子与代码块放哪，都由讲解角色按内容与学生偏好决定；`MEMORY.md` 的个人偏好优先。题目、lab、实验说明页都不归它管（规范见 `layered-practice`）。

## 一、要素（弱约束，根据实际情况调整，不必强加内容）

1. **真实场景**：说清楚某个概念解决的是什么麻烦、什么场景下用得上，可以仿照 `RESOURCES.md` 收集到的教材写
2. **术语先来历、后定义**：术语第一次出现时先知道它在历史上为什么被发明、解决了什么，再看到定义；中英对照
3. **权威教材的深度**：讲透前提、推导、边界与反例，不做速成课；简洁不等于浅
4. **动手**：
   - `kind: 实操` → 引导式实操：任务与断言由 `practice-evaluator` 出、落在 `lab/`；课件里对应一个动手块（内容由出题人给，位置与引入由你定）
   - `kind: 概念` → 轻量跟做：敲一条命令、改一行看变化、在输出里指出某个东西；不落 lab、不算交付物、分步且每步立刻能看到结果
   - 动手块与跟做步骤的标题按内容写中文阶段名（如"第 3 步 · 改造"）——**不要用 L1-L4 标步骤**（那是题目的层级词汇）

## 二、记忆与难度（弱约束）

分清**流畅度**（当场会复述）与**存储强度**（过段时间还记得住，目标）；用**合意困难**设计：检索练习（回忆而非重读）、间隔（分散到多次会话）、交错（混合相关主题）；难度落在最近发展区。

## 三、贯穿线索

每课连回三条：**最终目标**（这段知识与 `MISSION.md` 的关系）；**配套项目**（从早期就作为实操素材逐课埋线）；**工具对照**（编程类：亲手实现与现成库结果对照）。

## 四、复用与骨架（硬约束）

| 硬约束 | 怎么做 |
|---|---|
| 小节标题 | `<h2>` ≤14 字 |
| 起点 | 先读 `<subject_path>/assets/` 组件库；从 `<root>/templates/lesson.html` 拷起（顶栏、主题开关、提问提示、脚本引用已就位），**别删主题开关** |
| 文件名 | `<序号>-<节点id>.html`，序号 = 本节点在 `curriculum.yaml` 的 `nodes:` 里排第几（4 位补零，如 `0003`）、节点 id 原样照抄——上一课的「下节课」指针按这条规则预写，名字错一位那根指针就断。**归属（这课是哪个节点、挂主页路线图哪个位置）只认文件名**：页头的 eyebrow 是给学生看的可读文字（`0001 · 第一份能提交的代码`），写不写节点 id 都不影响归属 |
| 上/下节课指针 | 正文末尾 `.lesson-nav`：上一个、下一个节点取自 `nodes:` 顺序，`href` 按同一条命名规则写、标题用节点 `title`；第一课不写 `--prev`、最后一课不写 `--next`。「下节课」的课件通常还没产出，链接落空是正常的 |
| 组件与题目 | 新组件写进 `assets/` 不内联；题目块字段契约见 `templates/assets/quiz.js` 顶部注释，**嵌题时照抄出题人给的题面与答案**，要改先回去找它 |
| 交付形态 | 自包含 HTML（相对路径引用共享层与科目组件），浏览器直开可用；排版干净、适合反复回看 |

## 五、行文禁忌

1. 避免使用「肯定-否定」句式，如「不是...而是」。不要先假定学生会往你预想错误的方向想。
2. 避免使用生硬的类比与比喻，很多修辞你以为给学生讲清楚了但是反而加重了学生的理解负担，如「这个定义是从麻烦里长出来的」，简单的概念甚至不需要类比
3. 避免代入用户视角写行文（如「编译落到你手上，就是一个具体动作」「这轮你带走三个结论」）以及为了方便用户理解反而加重阅读负担的描述
4. 分清楚什么是重点，非重点的内容无须写得太详细。重点不明确也会显著提高阅读负担
