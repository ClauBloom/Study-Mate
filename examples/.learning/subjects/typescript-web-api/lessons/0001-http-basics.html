HTTP 基础：一次请求与响应里有什么

本节目标：能说清一次 HTTP 请求与响应里有什么——请求行、请求头、状态码分别在说什么，并能用 curl -v 亲手验证。

先看一个真实问题：按下回车之后发生了什么

你在浏览器地址栏输入一个网址，按下回车，网页就出现了。这一来一回，浏览器和服务器之间到底说了什么？

现在你只会写页面，这个问题可以先不管。但等你开始写后端——要自己接住别人的请求——它就是绕不过去的第一道坎：接口返回 404 时，你分不清是路径写错了、还是服务器根本没起来；前端说"参数传了"，你却看不出参数落在哪一段。原因都一样：不知道这两样东西长什么样。

先记住一句话

浏览器和服务器之间来回传的，本质是纯文本。这段文本谁都能看懂——包括你，不需要任何框架帮忙。今天这一课就是把它拆开看一遍。

把一次来回摊开看

用 curl -v 请求一个真实网址，屏幕上就是下面这个样子（* 开头的连接过程行略去）。> 开头的四行是客户端发出去的，< 开头的三行是服务器返回来的：

一次来回（curl -v 输出摘要）
12345678
> GET /menu HTTP/1.1 > Host: example.com > User-Agent: curl/8.7.1 > Accept: */* （空行——请求到此结束，GET 没有请求体） < HTTP/1.1 200 OK < Content-Type: text/html; charset=utf-8 < Content-Length: 1256

就三层：第一行说明要什么（或结果如何），中间几行是附加说明，空行之后才是正文。剩下的内容，只是把这三层逐个讲清楚。（Accept: */* 表示"什么格式都行"，浏览器在这里通常会写 text/html。）

这些词的来历：先有麻烦，才有名字

请求行、状态码、请求头——这三个词听着像要背的术语。其实每一个都是为了解决一个具体的麻烦才被造出来的。先看它解决什么问题，再看它叫什么名字。

请求行：让服务器知道"你要什么"

先有麻烦：上世纪 90 年代初，一台服务器上要放很多份文档。浏览器连上来只说一句"给我东西"，服务器不知道给哪一份，只能把整个目录列出来让人点。更要命的是，下一个人的文档站也在同一台机器上，服务器还得先判断"你到底在跟哪个网站说话"。

于是有了：把"要什么"压进第一行——方法、路径、协议版本，用空格隔开。这就是 请求行（Request Line）：

请求行
1
GET /menu HTTP/1.1
  • GET 是方法：不只是"给我看看"，还隐含"这个动作不该改动服务器上的东西"
  • /menu 是路径：要哪一份东西
  • HTTP/1.1 是协议版本：双方按哪一版规矩说话

定义：请求行是 HTTP 请求的第一行，由「方法 + 路径 + 协议版本」三部分组成，用空格分隔。

状态码：让双方对"结果"有一致的说法

先有麻烦：服务器处理完了，总得告诉浏览器结果。最早的思路是把说明跟正文混在一起写——"找不到页面，请点这里返回"。可机器读不懂人话：浏览器没法凭一句话判断该不该重试、该不该弹登录框、该不该把这个结果存进缓存。

于是有了：把结果压缩成三个数字，放在响应的第一行。这就是 状态码（Status Code），首位数字就是大类：2xx 成功、3xx 去别处拿、4xx 你的请求有问题、5xx 我这边出错了。

状态码它解决什么问题你该做什么
200成功，正文就是你要的东西直接解析正文
404"这个路径上没有东西"检查路径拼写、资源 id 是否存在
500"我这边炸了，跟你无关"看服务端日志——问题不在你的请求里

定义：状态码是 HTTP 响应第一行里、紧随协议版本的那个三位数字，用来表明这次请求的处理结果：200 表示成功，404 表示请求的资源不存在，500 表示服务端内部出错。

常见误区

把状态码当成要背的数字表。它不是编号，是分类：先看首位判断责任方，再看后两位判断具体原因。404 和 500 的区别不是"4 和 5"，而是"你错了"和"我错了"——这条判断决定你接下来该改请求还是该翻日志。

请求头：塞不进行里的附加说明

先有麻烦：请求行只有一行，能放的信息有限。可服务器还需要知道一堆零碎事：你说的是哪种语言、能接受什么格式、带宽够不够收压缩包、你的登录凭证是什么。这些信息既不属于"要什么"，也不能全塞进路径。

于是有了：在请求行后面追加若干行 名字: 值。这就是请求头（Request Header），与响应里的响应头成对出现，统称 HTTP 头（HTTP Headers）：

请求头
123
Host: example.com Accept: text/html Accept-Encoding: gzip

定义：请求头是请求行之后、空行之前的若干行「字段名: 值」，用来承载不属于请求行的附加信息，例如目标主机（Host）、可接受的响应格式（Accept）、是否接受压缩（Accept-Encoding）、身份凭证（Authorization）。

所以请求头与响应头是两回事：请求头是浏览器告诉服务器的，响应头是服务器告诉浏览器的，名字相似、方向相反——比如 Accept（我能收什么）只在请求里，Content-Type（我发的是什么）两边都会出现。

动手：亲手打一次请求

这节课的知识，最终要接上你的目标——独立做出一个能部署上线的订单 API。上线之后你排查问题的第一现场，就是这段原始文本。所以别光看，亲手打一次：

L1 理解

用 curl 找状态行

第 1 步　打开终端，敲：

curl -v https://example.com

第 2 步　在输出里找到 < 开头的那一行（状态行），它长这样：

< HTTP/2 200

如果这条连接走的是 HTTP/1.1，它会多一个原因短语，写成 < HTTP/1.1 200 OK。两种写法里中间那个 200 都是状态码。先别看别的，先把这个数字指出来。

第 3 步　把网址改成一份不存在的路径，再打一次：

curl -v https://example.com/no-such-page

第 4 步　对照两次的这一行：第一次是 200，第二次大概率是 404。同一台服务器、同一个方法、同一个 Host，只有一个数字变了——这就是状态码在做的事：报告结果，而不是报告内容。

第 5 步　回到上面的输出，把这几个词和屏幕上的行对上号：哪一行是请求行、哪几行是请求头、哪一行是状态行。> 开头的请求那几行只有 -v 才会打出来。
